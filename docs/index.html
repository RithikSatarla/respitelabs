// Physical observability for robots in production

Observability for the robot's body.

Ember watches the code.Respite Labs watches the body.

Respite Labs checks that a robot arm is physically what its software thinks it is. When a crash or a change moves something, it tells you what moved, by how much and when. Then it writes the fix to the controller, re-checks the cell and calls it GO or NO-GO.

// 02 · Layers

Two layers. Two different jobs.

Ember's line is "Know what changed. Know what failed." It is a good line, and for software it is the right one: releases, logs, telemetry, fleet hardware, for the engineers who build robots. Respite Labs sits one layer down. It asks whether the robot's body still matches what the software believes, for the teams who run robots in production.

// software layerEmber
releases · logs · telemetry · fleet health · hardware scheduling
"Which release broke it?"
// physical layerRespite Labs
camera pose · tool offset · joint zeros · command timing
"Is this robot physically what its software thinks it is? If not, what moved? Put it back."

Ember tells you something changed. Respite Labs puts the robot back.

You can run both. Respite Labs reads LeRobot datasets, ROS 1 and 2 bags, MCAP and UR RTDE recordings today, so it can sit next to Ember or Foxglove as a plug-in.

// 04 · System

Find. Check. Fix. Certify.

A healthy robot's sensors agree. The joints follow the commands after a fixed delay. The camera sees the wrist where the encoders say it is. A table marker stays where it was bolted. Each fault breaks a different agreement in a different shape. Respite Labs fits the one explanation that brings the error back down to sensor noise. There is no AI model inside, so the same log always gives the same answer.
